## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Pre-deletion git tag → post-deletion working tree | The `legacy-snapshot-2013` tag is the only path back to the pre-deletion state if the deletion goes wrong. It MUST be pushed to origin before deletion so a different clone (or a worktree-disaster scenario) can recover. |
| Human approval gate → automated destructive command | A human checkpoint sits between Task 1 (tag) and Task 3 (delete) so the deletion is never auto-executed without confirmation. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | T (Tampering) | Loss of legacy tree without recovery path | mitigate | Task 1 creates an annotated tag at HEAD and pushes to origin; Task 2 (human checkpoint) confirms `git ls-remote` shows the tag before Task 3 deletes anything. |
| T-03-02 | D (Denial of Service) | Accidental deletion of `readkit.epub*/` working directories | mitigate | The deletion list in Task 3's action excludes those directories; the verify command asserts `[ -d readkit.epub ] && [ -d readkit.epub.giantleap ] && [ -d readkit.epub.mobydick.epub ]` to fail loudly if they were touched. |
| T-03-03 | R (Repudiation) | Untraceable destructive commit | mitigate | The commit message names the deletion list, points at `legacy-snapshot-2013`, and references CONTEXT.md D-06 for rationale. |
| T-03-04 | E (Elevation of Privilege) | Force-push or destructive remote operation | accept | The plan only pushes a new tag (additive); no force-push, no branch reset. The destructive operation is local to the working tree and recorded in a normal commit. |
</threat_model>
