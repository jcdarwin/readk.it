    ```
    The product has two consumers (the build script in `tools/build-book.ts` from Phase 10, and the browser drag-drop entry from Phase 9) of one isomorphic EPUB engine. The engine is built on three third-party packages with strict ownership:
    ```

    ```
    # `src/components/`

    Lit Web Components. Shadow DOM. No `unsafeHTML()` on EPUB-supplied content.

    ## Why

    The reader chrome is implemented as Lit Web Components (REQ BUILD-03, REQ READER-01). The chrome's job is to render sanitised chapter HTML — the moment that HTML enters the DOM is the moment XSS becomes possible (Pitfall 5: untrusted EPUB content as same-origin XSS vector).

    Lit's `unsafeHTML()` directive bypasses the framework's escaping. Calling `unsafeHTML(chapterHtml)` on EPUB-supplied content is the canonical way to ship a working XSS. Every chapter HTML insertion in this codebase MUST go through `src/engine/sanitise.ts` (Phase 5) which wraps DOMPurify. The components in this directory are the ONLY consumers of `sanitise()`.

    ## Enforcement

    - **Phase 1 (this phase):** invariant documented in this README. The Phase 1 dev shell (`src/components/readkit-app.ts`, landing in Plan 07 of this phase) renders only static text via Lit's `html` template — no `unsafeHTML` use, no EPUB content yet.
    ```

    ```
    Reactive controllers (PreferencesController, BookmarkController, LocationController, RouterController, DropzoneController). DOM-free, 100% Vitest-testable.

    ## Why

    Lit's reactive-controller pattern keeps imperative behaviour out of the components in `src/components/`. A controller owns a piece of state (preferences, bookmarks, location, route, the dropzone state machine) and its lifecycle is wired to the host component, not to a DOM event listener directly.

    Controllers in this directory must be **DOM-free** — no `document.querySelector`, no `window` references in business logic — so they are unit-testable in Vitest's Node environment without `jsdom`.

    Controllers DO depend on `src/stores/PersistenceStore` (Phase 3) for any state that survives a reload. Controllers do NOT touch `localStorage` or `IndexedDB` directly.
    ```

    ```
    # `src/stores/`

    `PersistenceStore` is the only writer to IndexedDB / localStorage. No component touches storage directly.

    ## Why

    Pitfall 7 in `.planning/research/PITFALLS.md` is "cross-book persistence leakage". When multiple components touch `localStorage` directly, with overlapping key strategies, you eventually get publication A's theme leaking into publication B (or worse, publication A's bookmarks). The defence is a single store that namespaces every read and write by `bookId(metadata)` (derived from `dc:identifier` with content-hash fallback).

    `PersistenceStore` (Phase 3) is the canonical namespacing wrapper. It is schema-versioned (so a future migration doesn't lose data), backed by IndexedDB by default, and falls back to `localStorage` only when `IndexedDB` is unavailable (e.g. some `file://` runtimes).

    No code in `src/components/`, `src/controllers/`, or anywhere else may call `localStorage.setItem` / `indexedDB.open` directly.

    ## Enforcement

    - **Phase 1 (this phase):** invariant documented in this README. Store does not exist yet.
    - **Phase 3:** `PersistenceStore` lands here. A Vitest test asserts cross-book leakage is impossible (book A's theme-dark vs book B's default).
    - **Phase 8:** end-to-end Playwright test asserts the cross-book leakage invariant on real reader UI.

    ## Forward references

    - Phase 3 (Persistence Backbone) — `PersistenceStore` + `bookId()` helper land here.
    ```
